Overview

The AI Resource Intelligence Directory is a static HTML site. Every page is a standalone file that loads one or more JavaScript datasets from data/. Filtering, sorting, pagination, search, deep links, and the catalog terminal run entirely in the browser.

There is no application server, database, authentication layer, or analytics pipeline. Datasets, icons, and the static JSON files are bundled with the site. The only automatic external requests are the Tailwind CDN and Google Fonts; the Web3Forms endpoint is contacted only when someone submits the resource form.

Datasets and schemas

Records were extracted from the DevSpireHub AI knowledge base file ai-tools-models-developer-resources.md. The upstream repository is no longer publicly reachable; the extraction persisted in this project is the retained copy. Presentation code never writes to these files.

Shared fields: id, name, description, category, source_category, official_url, pricing, license, tags, evidence, verified, status, icon.

Policy: a field the source does not state stays null, empty, or absent. Model parameter counts and context windows are never estimated; cards show — where no figure exists.

Totals: every count on every page is computed from the loaded arrays. No page hardcodes a record total.

Catalog terminal

terminal.html is a read-only console with a fixed command table: help, stats, list, search, show, categories, open, and clear.

The page contains no eval, no dynamic function construction, no shell bridge, no filesystem access, and no network calls. Unknown commands are rejected by name lookup. Output is written with textContent, so typed markup is displayed as text.

Static API

api.html documents four generated files: api/catalog.json (manifest with counts and SHA-256 checksums), api/tools.json, api/models.json, and api/developer-resources.json.

These are static assets, not a hosted service. There is no base URL, authentication, versioning service, write endpoint, or uptime guarantee. Browsers block fetch() from file://; serve the folder over HTTP to read them programmatically, or use the Open links on the API page.

Submissions

submit.html validates a proposed record and sends it to the official Web3Forms endpoint, https://api.web3forms.com/submit. The page reports success only when Web3Forms returns success: true; failed or timed-out requests keep every entry on screen and show the reason.

The access key lives in data/site-config.js. A Web3Forms access key is a public routing identifier that is visible in the page source by design, not a secret. The repository ships with an empty key, so sending stays disabled until the deployer adds their own key. Recipient addresses are held in the Web3Forms account and are not embedded in this site.

Every submission is pending manual moderation. Nothing is added to a dataset or published automatically, and a successful Web3Forms response confirms delivery only. A JSON receipt is offered locally for the submitter's records. Spam controls include a hidden honeypot field, client-side duplicate suppression, and any filtering enabled in the Web3Forms account.

Limitations

  • The catalog is a static snapshot. Pages display the recorded last_verified dates; nothing polls upstream services.
  • Upstream source links can change or disappear. Evidence links are recorded as-is.
  • Search is client-side substring matching, not a ranked search service.
  • A submission receipt confirms that Web3Forms accepted the request; it does not confirm approval, publication, or inclusion in a dataset.
  • There is no hosted API, SLA, or machine-authenticated access.
